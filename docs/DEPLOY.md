# Deploy on Render (Blueprint) + custom domain

The web service is declared in `render.yaml`. The **database is Neon**,
provisioned outside Render, so the Blueprint creates a service but no database.

Local development is a separate document: [`LOCAL_SETUP.md`](LOCAL_SETUP.md).

## 0. Before you start

You need:

- the repo pushed to GitHub (`https://github.com/mjairumi/single-desk`),
- your **Neon pooled connection string** (Neon console → **Connect** → *Connection
  string*, the host ending in `-pooler…`), kept `?sslmode=require`,
- the Neon schema already created — see step 4 if you haven't run migrations yet.

## 1. Create the Blueprint

Render Dashboard → **New +** → **Blueprint** → pick the repo → **Apply**.

Render reads `render.yaml` and creates **`signal-desk-api`**, a Python web
service with `rootDir: backend`. On apply it will **prompt you for
`DATABASE_URL`**, because that variable is declared `sync: false` — that is
deliberate, so the credential is stored as a Render secret and never committed.
Paste the Neon pooled URI.

Everything else is set for you: `SECRET_KEY` is generated by Render
(`generateValue: true`), and the token TTLs and `PYTHON_VERSION` come from the
file.

Build and start commands:

```
buildCommand: pip install -r requirements.txt
startCommand: alembic upgrade head && gunicorn -k uvicorn.workers.UvicornWorker \
              app.main:app --bind 0.0.0.0:$PORT --workers 2 --timeout 60
```

`alembic upgrade head` runs on every boot. It is idempotent — a no-op once the
schema is current.

Watch the deploy log; when `GET /api/health` returns `{"ok":true}` you're live at
`https://signal-desk-api.onrender.com` (Render appends a suffix if that hostname
is taken — use whatever the dashboard shows).

## 2. Region — keep it next to Neon

`render.yaml` sets `region: singapore` because the Neon endpoint is
`ap-southeast-1`. This matters more than it looks: a measured round-trip to Neon
from a co-located client is **~75 ms**, and a single `/api/sync` write costs
several round trips (user-row lock → flush → commit → clock re-read). Putting
the service in Oregon against a Singapore database roughly triples the latency of
every write.

If you move the database, move the service to match.

## 3. Set CORS for the extension

The web app is served by FastAPI at the same origin and needs no CORS entry. The
extension is a separate origin and does.

1. Load the extension unpacked (`chrome://extensions` → Developer mode → Load
   unpacked → `extension/`) and copy its **ID** — the Options page shows it.
2. Render → the service → **Environment** → set `CORS_ORIGINS` to your real
   values, e.g.
   `https://app.your-domain.com,chrome-extension://<that-id>`.
3. Save. This restarts the service; no code redeploy needed.

Also update `host_permissions` in `extension/manifest.json` to your deployed
origin — it still ships the `https://YOUR-DOMAIN.com/*` placeholder, and the
extension cannot call an origin that isn't listed there.

## 4. Migrations

The schema is applied from your machine, pointed at Neon:

```bash
cd backend && source .venv/bin/activate
set -a && . ./.env.production && set +a
alembic upgrade head
```

Confirm the target before running it — this is the one command that writes to
production:

```bash
python -c "from app.config import Settings; print(Settings().database_url.split('@')[1].split('?')[0])"
```

For later model changes: `alembic revision --autogenerate -m "…"` against a
**dev** database, commit the file under `backend/migrations/versions/`, and the
next deploy applies it via `startCommand`. On a paid plan, prefer moving it to
`preDeployCommand: alembic upgrade head` so a failed migration doesn't take the
service down mid-boot.

## 5. Custom domain

Render → the service → **Settings → Custom Domains** → add
`app.your-domain.com` (or the apex). Render shows the DNS record to create:

- subdomain → a **CNAME** to the `onrender.com` host;
- apex/root → Render's **ANAME/ALIAS** or A records (follow what Render displays).

TLS is issued automatically once DNS resolves. Then add the new origin to
`CORS_ORIGINS`, and point the extension's **API base** (Options page) at it.

## Cost & durability

- **Free Render web services spin down when idle** (~30–60 s cold start). Neon's
  free tier also autosuspends. Together that makes the first request after a
  quiet period slow — fine for trying it, poor for daily use. `pool_pre_ping=True`
  in `app/database.py` means a suspended-then-resumed database recovers rather
  than erroring.
- For real use, move the service to at least `starter`. **Confirm current plan
  names and prices at <https://render.com/pricing>** — they change.
- Backups are Neon's job now: Neon keeps point-in-time history on paid plans
  (and a shorter window on free). The app has no export endpoint yet, so
  `pg_dump` against the Neon connection string is still worth scheduling.

## Verifying a deploy

```bash
curl -s https://<your-service>.onrender.com/api/health      # {"ok":true}
```

Then run the full contract test against the deployed URL:

```bash
cd backend && source .venv/bin/activate
BASE=https://<your-service>.onrender.com python tests/manual_smoke.py   # -> SMOKE OK
```

**This writes to whatever database the service points at.** It signs up a user
and pushes items and sessions. Against production, delete the account afterwards
(`users` cascades to items, sessions, and refresh tokens):

```sql
DELETE FROM users WHERE email LIKE 'smoke+%@example.com';
```
